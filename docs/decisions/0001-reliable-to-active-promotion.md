# ADR 0001: Promote reliable accounts into the active scrape list

Date: 2026-05-07
Status: Accepted

## Context

The pipeline kept two separate account lists with no automatic link between them:

1. **Active scrape input** — the `Accounts` tab in the Google Sheet (falls back
   to `accounts.json`). This is what `fetch_posts_via_apify()` actually feeds
   to Apify on each run.
2. **Reliability watchlist** — `outputs/reliable_accounts.csv`, generated by
   `recurring_accounts.py` from past `All_Events` history. Catalogues accounts
   that have produced repeat or branded-series events.

Nothing promoted entries from list 2 into list 1. An account could rack up 30+
historical extracted events on the watchlist and still be missing from the
active list — meaning Apify was never asked to scrape it.

Concrete trigger: `interludseries` had 32 occurrences in `reliable_accounts.csv`
but had not been actively scraped since Feb 5 2026. A clear March 30 post
(`DWg2XDvkY06`, "$1 Interlude") was never fetched, never reached Gemini, never
appeared in any output. Confirmed via inspection of `pipeline_checkpoint.pkl`
(post ID absent from the 34,925-entry `processed_posts` set).

While diagnosing the same case we also discovered that the `Accounts` tab
contained `interludeseries` — a one-character typo — which would have silently
returned no posts forever. The promotion step doubles as a self-heal for that
class of bug because reliable handles are derived from real extractions and
therefore correctly spelled.

## Decision

After each pipeline run, when `recurring_accounts.refresh()` is called, append
qualifying reliable accounts into the `Accounts` tab.

An account qualifies when **all** of:

- It is pattern-matched as recurring by the existing detector (day-of-week
  plural / recurrence keyword / repeated branded name).
- `Distinct Posts >= 3` (configurable via `--threshold`). We gate on **distinct
  post URLs**, not raw `Occurrences`, because cumulative weekly re-exports
  inflate row counts: an account whose single post appeared in 30 weekly
  exports has `Occurrences=30` but `Distinct Posts=1` — that is not real
  evidence of recurring activity.
- The most recent `post_date` / extraction timestamp is within the last 180
  days (configurable via `--recency-days`; pass `0` to disable).
- It is not already present in the `Accounts` tab (case-insensitive).

The typo detector handles a related-but-distinct case: accounts that *should*
be active under a corrected spelling but are not. It emits suggestions for
manual review rather than auto-correcting, since `interludseries` →
`interludeseries` is unambiguous but `mimi.lano` → `miamilano` is probably a
different person.

`--dry-run` previews promotions without writing. The existing `accounts.json`
↔ `Accounts` tab sync in `main.py` propagates the additions on next read, so no
secondary write path is needed.

A typo detector runs alongside promotion: any active-list handle within
Levenshtein distance ≤ 2 of a reliable handle (and not exactly equal to one) is
flagged for manual review.

## Consequences

- Newly-recurring accounts auto-flow into the active scrape list — fewer silent
  misses of known-good event sources.
- Apify usage grows incrementally, bounded by the reliability bar. Each newly
  promoted account adds `apify_posts_per_profile` posts per weekly run.
- We have **not** solved the onboarding-backfill problem: a freshly-promoted
  account whose announcement post is older than `apify_newer_than_days` is
  still invisible to the rolling Apify scrape. This was deliberately deferred
  as too expensive given current quota use; revisit if missed-event reports
  continue.
- The recency filter uses our extraction history, which is self-perpetuating:
  if an account was excluded from scraping for a long stretch, our
  `_last_seen` for it lags reality. The 180-day default is generous enough to
  tolerate this for normal pauses; manual override (`--recency-days 365` or
  `--recency-days 0`) handles backfill scenarios.
